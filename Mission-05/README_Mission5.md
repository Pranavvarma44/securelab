# Mission 5: The Race

## Objective

Create a race condition and then protect the critical section with a mutex.

## Concepts

- Shared state
- Critical section
- Race condition
- Mutex
- Threads and synchronization

## Experiment

The program creates two POSIX threads. Each thread increments the shared global variable `counter` 1,000,000 times. Therefore, the expected final value is:

```text
2 threads × 1,000,000 increments = 2,000,000
```

### 1. Unsynchronized experiment (without a mutex)

In `race_demo.c`, the worker loop contains an unprotected increment:

```c
counter++;
```

Compile the program without optimization, as specified in the handout:

```bash
gcc -Wall -Wextra -O0 -pthread race_demo.c -o race_demo
```

Run it several times:

```bash
./race_demo
./race_demo
./race_demo
./race_demo
./race_demo
```

The actual value may be lower than 2,000,000 because concurrent read-modify-write operations can overwrite one another. The exact result can vary between runs; a run that happens to print 2,000,000 does not prove that the race is absent.

Example values observed during this experiment:

| Run | Expected | Actual |
|---:|---:|---:|
| 1 | 2,000,000 | 1,090,288 |
| 2 | 2,000,000 | 975,226 |
| 3 | 2,000,000 | 991,470 |
| 4 | 2,000,000 | 1,070,444 |
| 5 | 2,000,000 | 1,016,213 |

### 2. Mutex-protected experiment

Protect the increment with the mutex:

```c
pthread_mutex_lock(&lock);
counter++;
pthread_mutex_unlock(&lock);
```

Compile and run:

```bash
gcc -Wall -Wextra -O0 -pthread race_demo.c -o race_demo
./race_demo
```

Expected output:

```text
Expected: 2000000
Actual  : 2000000
```

The mutex ensures that only one thread at a time executes the protected increment. The two threads still run concurrently, but access to the shared counter is serialized.

## Theory Questions

### Q13. Why can the unsynchronized result be lower than expected?

When two threads access and update the same shared counter without synchronization, their operations can overlap. Both threads may read the same old value and then write back the same incremented value. One update is then lost. This is why the final counter can be lower than the expected 2,000,000.

### Q14. Which region is the critical section?

The shared-counter update, `counter++`, is the critical operation. In the protected version, the critical section is the region between `pthread_mutex_lock(&lock)` and `pthread_mutex_unlock(&lock)`. The mutex ensures that only one thread at a time executes this region.

### Q15. Why can a race condition become a security vulnerability?

If a security-sensitive operation is performed without correct synchronization, an attacker may be able to influence the timing of concurrent operations. This can cause checks and updates to occur in an unsafe order, potentially allowing unauthorized access, data corruption, or bypass of a security check.
